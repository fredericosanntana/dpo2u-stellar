## Design decisions (honesty-relevant)

- **Interface injection over hard dependency.** The gateway accepts an injected `DefindexOperatorClient` (and `DefindexAttestationVerifier`) instead of importing `@defindex/sdk`. This keeps tests network-free (plan requirement #2) and avoids overclaiming a live DeFindex integration beyond the code actually added. `package.json` was therefore **not** modified — `@defindex/sdk` is documented as the adapter target (with a thin-wrapper sketch in `defindex-policy-types.ts`), not a consumed dependency. The plan said to add it "if actually used"; it is not yet actually imported, so adding it would have been dishonest dependency padding.
- **Operator-surface only.** The six gated operations (`createVault`, `rebalanceVault`, `rescueVault`, `distributeFees`, `pauseStrategy`, `unpauseStrategy`) are exactly the role-gated ones. Deposits/withdrawals are deliberately absent; both the PRD and the code comments explicitly state DeFindex deposits have no on-chain allowlist and any deposit policy would be off-chain UX only.
- **Verifier compatibility.** `DefindexAttestationVerifier.verify(args)` is structurally satisfied by the existing `AttestationClient` — no change to attestation-client behavior.
- **Fail-closed.** `found && verdict === 'PASS'` is the only allow path; missing / FAIL / REVIEW all deny with stable, machine-parseable reason prefixes (`ALLOW:PASS`, `DENY:NO_ATTESTATION`, `DENY:FAIL`, `DENY:REVIEW`).
- **Soroban Symbol safety.** All default `use_case_id`s (`defindex_*_v1`) are ≤32 chars / `[a-zA-Z0-9_]`, so they pass `AttestationClient`'s validation; a test asserts this.

## Test coverage vs. plan requirements

- PASS attestation authorizes an operator action ✔ (`createVault` PASS → allowed)
- FAIL or missing attestation denies it ✔ (missing → `DENY:NO_ATTESTATION`; FAIL → `DENY:FAIL`; REVIEW → `DENY:REVIEW`)
- Policy mapping for ≥2 operation types ✔ (`createVault`/`rebalanceVault`/`distributeFees` → distinct roles + use cases)
- Execution helper does NOT call DeFindex client when denied ✔ (spy `createVault`/`rebalance` assert `not.toHaveBeenCalled()` on deny; assert called once on allow)

## Honest limitations / follow-ups

1. **No live DeFindex wiring yet.** The DeFindex client is an injected interface; there is no real `@defindex/sdk` adapter and no testnet transaction was prepared/signed/broadcast. Follow-up (PRD Phase 1): implement `DefindexSdkAdapter implements DefindexOperatorClient`.
2. **Role-as-contract is target, not built.** The strongest claim — a DPO2U policy contract occupying a vault role so authorization lives in protocol mechanics — is Phase 2. As with the ASP/SPP track (`docs/S8-EXTERNAL-ASP-BOUNDARY-REPORT.md`), the remaining boundary is governance/operational authority over a vault, not technical feasibility.
3. **Policy → role mapping is our choice, not a DeFindex constraint.** DeFindex lets the Manager perform most privileged ops; we split them across roles for least-privilege. The exact required signer per op needs confirmation (see PRD §8 open questions).
4. **`@defindex/sdk` method shapes are modeled from docs, not verified against the installed package.** `createVault`/`rebalance`/etc. signatures in `defindex-policy-types.ts` mirror documented surfaces and must be reconciled with the real SDK when building the adapter.
5. **Evidence-hash binding is caller-supplied.** The gateway takes a 64-char hex evidence hash verbatim; computing/canonicalizing the action-payload hash is left to the compliance engine and is not implemented here.
6. **Pre-existing npm advisory** (1 high) is unrelated to this slice and was left untouched.
